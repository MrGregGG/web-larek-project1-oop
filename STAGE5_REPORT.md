### Корзина и количество

Утверждённая корзина содержит уникальные ID: количество одной позиции всегда 1. В BasketItemData нет quantity, а в #card-basket нет счётчика количества или кнопок +/−. Поэтому BasketItem показывает порядковый номер index, а Basket — число переданных DOM-позиций в заголовке «Корзина (N)». Новые поля и управление количеством позиции не выдумывались.

Basket не вычисляет стоимость по DOM/ценам и не обращается к модели. Изменение количества товаров и суммы проверено через существующий BasketModel в контролируемом тесте. При пустом items рендерится один переиспользуемый li «Корзина пуста» и оформление выключается даже при ошибочно переданном checkoutDisabled=false. Это защита пустого отображения, а не замена проверки модели/координатора. Цена 0 отображается и не блокирует оформление непустой корзины.

### Формы, ошибки и ожидание

Form не проверяет обязательность/regex: он получает готовый ValidationResult и disabled. Текст ошибки каждого поля и serverError выводятся через textContent в .form__errors с role=alert. Для известных inputs обновляется aria-invalid. Валидная форма с disabled=true блокирует submit, ввод и, в OrderForm, обе кнопки оплаты.

Подписка input проверяет конкретный найденный DOM-элемент; посторонний input с поддельным name игнорируется. Ввод передаётся точно, без trim, чтобы валидацией и нормализацией продолжала заниматься модель. Если значение при обратном render не изменилось, input.value не присваивается повторно: курсор сохраняется.

Submit вызывает preventDefault и отправляет намерение только при разрешённой кнопке и отсутствии disabled. Одна регистрация обработчика не означает запрет двух отдельных пользовательских отправок: будущий координатор должен синхронно установить pending и повторно отобразить disabled. Локальный координатор/HTTP/очистка данных на этом этапе не реализованы.

serverError сам по себе не делает модель невалидной. После снятия pending валидная форма допускает ручной повтор, сохраняя переданные значения. Выбор card/cash — внутренние значения типов и HTML. Поддержка cash сервером остаётся прежним открытым вопросом этапа 3; никаких заказов для её проверки не отправлялось.

### Жизненный цикл

Все DOM-слушатели создаются в конструкторах через Component.listen. Повторные render не добавляют подписок. Унаследованный destroy удаляет точные callback, повторный destroy безопасен; render уничтоженной View запрещён. View не подписываются на событийную шину и не вызывают offAll.

Удаление позиции из Basket не уничтожает чужую BasketItem автоматически. Владельцем дочерних View остаётся вызывающий код будущего координатора; в тесте старые строки явно уничтожаются перед заменой. Success не очищает модели и не закрывает Modal самостоятельно.

## 5. Как проверить на Windows

В корне полного проекта с установленными рабочими зависимостями:

```powershell
npx --no-install tsc --noEmit --skipLibCheck
npx --no-install eslint --max-warnings=0 src/components/Basket.ts src/components/BasketItem.ts src/components/base/Form.ts src/components/OrderForm.ts src/components/ContactsForm.ts src/components/Success.ts
npx --no-install eslint --env node --max-warnings=0 scripts/check-ui.mjs tests/checkout-ui.browser.mjs
node scripts/check-models.mjs
node scripts/check-shop-api.mjs
npm run build
node scripts/check-ui.mjs --stage5 --serve
```

Открыть в обычном Chrome/Edge напечатанный адрес `http://127.0.0.1:8084/`. Все 73 сценария выполняются автоматически; результат появится на странице и в терминале. Ожидается «UI этапа 5: 73/73; ошибок: 0», но новый Windows-результат пока не получен. Терминал нужно оставить открытым; остановка — Ctrl+C. При занятом порте добавить `--port=8085`.

Для браузерной регрессии этапа 4 после остановки стенда:

```powershell
node scripts/check-ui.mjs --serve
```

Ожидаемый результат прежнего набора — 38/38. Оба стенда изолированы от src/index.ts и не запускают магазин/API. Для тестов не нужны новые зависимости или реальные заказы.
