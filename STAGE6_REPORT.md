## 2. Реализация AppPresenter

Сохранена утверждённая архитектурой форма координатора: **функция createApp в src/app.ts**, выполняющая роль AppPresenter. Она создаёт одну существующую EventEmitter, Api/ShopApi, CatalogModel, BasketModel, OrderModel и View. AppOptions позволяет внедрить root, существующую шину, IShopApi и адреса для тестов без изменений прикладных контрактов. Возвращаются ready, reloadCatalog и destroy.

| Зона | Реализованное поведение |
| --- | --- |
| Каталог | Автоматическая загрузка через loadCatalog → ShopApi → Api, загрузочный статус, пустой результат, ошибка и ручной повтор. Одновременно выполняется один GET. Невалидный JSON проверяет существующий адаптер |
| Карточки | Подготовка CatalogCardData, отображение реальных категорий и fallback other, существующая CDN-утилита. Клик открывает ProductPreview по ID из модели |
| Покупка | Добавление через BasketModel, защита null/дубля и корректная цена 0, счётчик, «Уже в корзине», список/индексы/сумма/удаление |
| Два шага | Значения и ValidationResult берутся из OrderModel. Проверяется текущий экран и валидность перед переходом. Черновик сохраняется после закрытия и ошибки |
| Отправка | Снимок через OrderModel.createOrder; pending ставится до await. Повторный submit и изменения/переходы во время отправки игнорируются; формы получают disabled |
| Подтверждение | Только проверенный результат ShopApi. Корзина и заказ очищаются после ответа; формы получают очищенные значения. Success открывается только если Modal остался открытым |
| Ошибка | Данные сохраняются, кнопка вновь доступна, показывается безопасное сообщение, возможен ручной повтор; автоматического POST-повтора нет |
| Закрытие | Крестик/overlay закрывают, внутренний клик не закрывает, Page разблокируется. Закрытие не отменяет ожидание сервера и не приводит к внезапному переоткрытию |

ScreenState и SubmissionState независимы. Одинаковый DOM-узел формы не вставляется повторно в Modal на каждом input: иначе браузер теряет фокус. Формы продолжают отвечать только за отображение и намерения, модели — за правила.

Каталожные карточки и строки корзины принадлежат координатору: он уничтожает старые экземпляры при замене/удалении. Формы/preview/корзина/успех переиспользуются. Подписки EventEmitter снимаются точными callback, offAll не используется. destroy идемпотентен; поздние GET/POST после уничтожения игнорируются. Физическая отмена запроса не добавлялась: существующий Api не поддерживает AbortSignal.

Page дополнен только кнопкой повторения и методом setCatalogRetry(visible, disabled). Кнопка публикует уже предусмотренное catalog:retry, удаляется при destroy и не меняет PageViewData. Скрытие дополнительно задаёт display:none, чтобы CSS .button не переопределял HTML hidden.

cash остаётся неподтверждённым контрактом. Существующий ShopApi отклоняет такой заказ до HTTP, координатор показывает его сообщение и сохраняет данные. Онлайн-оплата передаётся адаптером как online. Ни cash, ни ошибочный ответ не имитируются как успех.

## 3. Почему main.js был пустым и что проверено теперь

До интеграции src/index.ts импортировал только SCSS. MiniCssExtractPlugin извлекал CSS в отдельный файл; импорта и запуска приложения не было. Минификатору было нечего сохранять в основном JS. Это объясняет нулевой main.js предыдущего этапа; успешный build сам по себе не означал работающий магазин.

Теперь src/index.ts импортирует и вызывает createApp. `node scripts/check-app.mjs --check-only` проверяет наличие непустого dist/main.js, его подключение из production HTML и ожидаемый код приложения.

- Размер проверенного main.js: **95 463 байта**.
- SHA-256: `1f80e62aa6f8140ae0c7ff13ed40bd212c368b9a97ff967ec0aa90205d19af39`.
- Обычный production index.html по HTTP запускает именно этот файл, без тестового entry.
- Production-код загрузил **10 реальных товаров** с `https://larek-api.nomoreparties.co/api/weblarek/product/`; в этом прогоне выполнялся только GET.
- Подтверждение: `docs/testing/stage6-live-page-results.json`. Это выполнение в jsdom, а не визуальная браузерная проверка.

Существующие API_URL/CDN_URL не изменены. Если API_ORIGIN пустой, относительные значения разрешаются относительно подтверждённого публичного origin. Настроенный абсолютный API_ORIGIN сохраняется. Подключение к несуществующему backend локального dev-server по умолчанию не требуется.

## 5. Запуск обычного магазина и проверка на Windows

В ZIP есть готовый dist. Из корня проекта достаточно установленного Node:

```powershell
node scripts/check-app.mjs --check-only
node scripts/check-app.mjs
```

Открыть **APP_URL** из терминала, обычно `http://127.0.0.1:8087/`. Это обычный магазин с настоящим каталогом, без тестового entry и без автоматических заказов. Проверить карточки, изображения, preview, корзину, удаление и формы. **Не отправлять заказ реальному серверу в рамках приёмки.** Для отправки/подтверждения использовать только второй адрес, **CONTROLLED_CHECK_URL**, обычно `http://127.0.0.1:8087/__controlled/`: восемь проверок выполняются автоматически и результат отображается на странице и в терминале.

При занятом порте: `node scripts/check-app.mjs --port=8089`. Для остановки Ctrl+C. Не открывать index.html через file://; для загрузки API нужен HTTP. Публикация на GitHub Pages/внешний хостинг не выполнялась.

Для пересборки и полных проверок с уже установленными рабочими Windows-зависимостями:

```powershell
npx --no-install tsc --noEmit --skipLibCheck
npx --no-install eslint --max-warnings=0 src/app.ts src/index.ts src/components/Page.ts
npx --no-install eslint --env node --max-warnings=0 scripts/check-ui.mjs scripts/check-app.mjs tests/app.browser.mjs tests/production.browser.mjs
node scripts/check-models.mjs
node scripts/check-shop-api.mjs
npm run build
node scripts/check-app.mjs --check-only
node scripts/check-app.mjs
```

Дополнительные изолированные браузерные наборы, по одному после остановки предыдущего:
