## 3. Реализованные модели

### CatalogModel

Файл: [`src/models/CatalogModel.ts`](src/models/CatalogModel.ts).

- Приватный список товаров, экземпляр существующего `IEvents` в конструкторе.
- `items` возвращает копии списка и товаров.
- `setItems` сначала проверяет уникальность ID. При дубле бросает исключение, не меняет старый каталог и не отправляет событие. После успешной замены отправляет `catalog:changed` с `{ items }`.
- `getById` возвращает копию товара или `undefined`.
- Товар без цены разрешён в каталоге: запрет относится к покупке, а не к просмотру.

### BasketModel

Файл: [`src/models/BasketModel.ts`](src/models/BasketModel.ts).

- Приватный `Map<ProductId, BasketProduct>` обеспечивает уникальность по ID и порядок добавления.
- `add` возвращает `false` при повторе, null/отсутствующей/нечисловой/отрицательной/бесконечной цене либо переполнении общей суммы. Нулевая цена разрешена. Успешное добавление сохраняет копию товара.
- `has`, `remove`, `clear` соответствуют контрактам. Неуспешное удаление и очистка уже пустой корзины не создают событий.
- `getState` возвращает новые копии и вычисляет `count` и `total` из содержимого; независимых изменяемых полей итогов нет.
- После фактического изменения публикуется `basket:changed` со снимком `{ items, count, total }`.

### OrderModel

Файл: [`src/models/OrderModel.ts`](src/models/OrderModel.ts).

- Черновик начинается с `payment: null` и пустых строк; getter `draft` отдаёт копию.
- `setField` сохраняет типовую связь имени и значения. Во время выполнения отклоняет неизвестное значение способа оплаты и нестроковые текстовые значения. Повторное присваивание того же значения ничего не публикует.
- `validate` возвращает отдельные результаты для оплаты/адреса и контактов. Условия: card/cash и непустые после `trim()` адрес/email/телефон. Дополнительных ограничений длины и формата нет.
- `createOrder` проверяет обе формы, непустую корзину, уникальные ID и допустимые цены, заново считает сумму и проверяет соответствие переданных `count`/`total` фактическим товарам. Несогласованный снимок отклоняется, а не молча исправляется.
- Результат — `IOrder` с новым массивом ID, проверенным итогом и обрезанными по краям строками. Черновик и корзина не меняются, событие отправки не создаётся, HTTP не выполняется.
- `clear` явно сбрасывает все поля и публикует `order:changed`; повторный сброс пустого черновика не создаёт события.
- `order:changed` содержит копию черновика и актуальную валидацию.

## 4. Почему приняты эти решения

1. Используется существующая шина: модели принимают `IEvents`, публикуют три события из утверждённого `AppEventMap`. Второй EventEmitter или базовый инфраструктурный класс не создан.
2. Все импорты в моделях — `import type`; исполняемых зависимостей от DOM, View, HTTP и утилит браузера нет. Проверки используют настоящий существующий EventEmitter, а не его подмену.
3. Копирование необходимо, потому что TypeScript `readonly` сам по себе не защищает от изменения объекта в JavaScript. Все поля утверждённого IProduct скалярные, поэтому копирования объекта достаточно. Снимки не замораживаются, но их изменение не меняет модель.
4. Дубль и непокупаемый товар возвращают `false` согласно IBasketModel; невалидный заказ бросает исключение согласно IOrderModel. Проверка API/нормализация JSON по-прежнему находится за пределами этапа.
5. Формирование IOrder не означает подтверждённую покупку. Данные сохраняются до явного вызова clear будущим координатором после успешного ответа сервера.
6. Дополнительных npm-зависимостей нет. Для воспроизводимых проверок добавлены небольшой Node-runner и тесты стандартного `node:test`, без изменения npm scripts или конфигураций.
