## 2. Почему реализация устроена так

- Все DOM-ссылки находятся один раз в конструкторе через существующий ensureElement. Клонирование шаблонов в тестовом вызывающем коде выполняет существующий cloneTemplate. Вторых DOM-утилит и EventEmitter нет.
- UI не получает Model/Api и не вычисляет суммы/количество, не классифицирует товары, не формирует CDN-адрес. CatalogCard принимает готовый CatalogCardData; Page — готовый PageViewData.
- Подписки создаются только в конструкторе через Component.listen. Ни render, ни повторные open/close не добавляют DOM-обработчики.
- View только публикуют существующие события и не подписываются на шину. destroy не вызывает offAll и не ломает подписки других частей приложения.
- После destroy повторный render/open запрещён; повторный destroy безопасен. Modal.close после уничтожения ничего не делает. Modal.destroy использует finally для снятия своих обработчиков даже при исключении стороннего подписчика modal:closed.
- Page и Modal получают DOM-узлы, а не экземпляры дочерних View. Они не вызывают destroy чужих карточек: владельцем жизненного цикла остаётся вызывающий код будущего координатора.
- Текст вставляется через textContent. Строки с HTML не исполняются и не создают элементы. Эти проверки включены в браузерный набор.

## 5. Конкретное ограничение браузера

Браузер не смог открыть локальный HTTP-стенд (ERR_CONNECTION_REFUSED). Статический HTTP-адрес среды отклонён ERR_BLOCKED_BY_CLIENT. Прямое открытие file-протокола также запрещено политикой браузера. Переходы к недоступному/запрещённому адресу не засчитываются как выполнение тестов. Ограничение не обходилось через неразрешённые browser/CDP-интерфейсы.

Это относится к текущему окружению проверки и не доказывает поломку проекта на Windows. Реальная загрузка страницы, визуальная оценка, работа мышью и фактическое прохождение 38 UI-тестов пока остаются открытыми. Гарантия отсутствия UI-регрессий в браузере не заявляется.

## 7. Устройство тестового runner

scripts/check-ui.mjs компилирует текущий TS по исходному tsconfig во временную папку как CommonJS. Отдельный fixture entry использует уже скомпилированный JS и исходный SCSS. Для HTML/CSS/assets переиспользуется существующий Webpack config, но entry/output и режим минимизации задаются только в памяти тестового процесса. Конфигурационный файл приложения не меняется.

Предварительная TS-компиляция позволяет не вызывать существующий Babel TS-loader для тестового fixture. Это не исправление/отключение Babel в самом проекте. Исходный src/public копируется только в тестовую папку для favicon и manifest. Временные файлы удаляются при завершении runner.

Режим `--serve` сохраняет стенд открытым после получения результатов. Без этого флага HTTP-стенд завершается после отчёта браузера и устанавливает exit code по числу ошибок. Режим `--export=<папка>` создаёт самостоятельный статический стенд без HTTP-сервера; в нём результат доступен на странице. Экспорт в произвольную папку применяется только по явно указанному пути.
