Отправка online-заказа реализована по документации поставщика и проверена контролируемыми ответами; реальные заказы не создавались. ## 1. Источники и подтверждённые адреса

Первичный источник контракта — [Postman-коллекция на самом сервере](https://larek-api.nomoreparties.co/weblarek.postman.json), полученная HTTP 200. Её variable baseUrl совпадает с работающим сервером. Чужие студенческие реализации и Film/Afisha api.yml не использовались как спецификация. Найденный официальный учебный backend bad-server имеет другой контракт и не использован для подмены этого API.

| Назначение | Адрес | Подтверждение |
| --- | --- | --- |
| Origin | `https://larek-api.nomoreparties.co` | Корневой GET вернул `{ "result": "OK" }` |
| API base | `https://larek-api.nomoreparties.co/api/weblarek` | Variable коллекции поставщика |
| Каталог | `GET https://larek-api.nomoreparties.co/api/weblarek/product/` | Реальный HTTP 200, 10 товаров |

Swagger/OpenAPI по проверенным `/api/docs`, `/api/docs-json`, `/openapi.json`, `/docs`, `/swagger.json` не найдены; отсутствие по этим путям не доказывает отсутствие документации вообще. Реальная документация найдена по ссылке коллекции выше.

## 2. Реальные данные и отдельные примеры документации

Реальный ответ каталога на момент проверки: объект с `total: 10` и `items`, содержащим 10 товаров. Полные исходные байты ответа сохранены в `docs/api/live-catalog.json`. Один реальный товар:

```json
{
  "id": "854cef69-976d-4c2a-a18c-2aa45046c390",
  "description": "Если планируете решать задачи в тренажёре, берите два.",
  "image": "/5_Dots.svg",
  "title": "+1 час в сутках",
  "category": "софт-скил",
  "price": 750
}
```

Реальный товар с отсутствующей ценой:

```json
{
  "id": "b06cde61-912f-4663-9751-09956c0eed67",
  "description": "Будет стоять над душой и не давать прокрастинировать.",
  "image": "/Asterisk_2.svg",
  "title": "Мамка-таймер",
  "category": "софт-скил",
  "price": null
}
```

В полученных данных id, description, image, title, category — строки. price — число либо null. Во всех 10 товарах поля присутствуют; остальные поля не додумывались. Наблюдённые категории: софт-скил, другое, дополнительное, кнопка, хард-скил. Они не объявлены закрытым enum: это наблюдённые значения текущего каталога, не обещание неизменяемости схемы.

`docs/api/live-product.json` — реальный ответ отдельного товара, `live-not-found.json` — реальная ошибка неизвестного товара. `docs/api/verification.json` содержит проверенные URL, статусы и доступные HTTP-заголовки. Снимки фиксируют дату проверки, не заменяют текущий сервер.

В `docs/api/provider-order-examples.json` явно помечены **примеры документации поставщика**, а не ответы на новые заказы. Коллекция показывает request body с payment=`online`, email, phone, address, total и items (массив id). Пример успеха: `{ "id": "28c57cb4-3002-4445-8aa1-2a06a5055ae5", "total": 2200 }`. Примеры ошибок HTTP 400 имеют `{ "error": "..." }`: неизвестный товар, неверная сумма, отсутствующий адрес.

## 3. Реализация и разделение данных

Входящий результат существующего Api принимается как unknown, а не приводится к IProduct[]. `productData.ts` проверяет весь ответ и получает ServerProductListDto; затем явно создаёт новые IProduct/ProductList с только разрешёнными полями. DTO семантически отделены в `src/types/api.ts`; Pick/Omit и существующий ApiListResponse используются вместо повторного объявления одинаковых базовых контрактов.

ShopApi реализует неизменённый IShopApi и принимает один существующий Api. Ни fetch, ни второй HTTP-клиент/брокер внутри адаптера не создаются. Все HTTP-операции делегированы Api.get/Api.post. Модели не изменены и HTTP не выполняют.

Узкая функция `loadCatalog(shopApi, catalog)` выполняет один координирующий шаг. Она передаёт items в CatalogModel только после успешной проверки всего ответа. Ошибка сохраняет прежний каталог; частичная загрузка одного корректного товара перед ошибкой другого не допускается. Это не координатор всего приложения.

Пример подключения из будущего координатора с уже созданной моделью:

```ts
const shopApi = new ShopApi(new Api(API_URL), CDN_URL);
await loadCatalog(shopApi, catalog);
```

`src/index.ts` не менялся, автоматический запрос из страницы не добавлялся. На этом этапе проверен вызываемый интеграционный модуль; UI отсутствует.

## 4. Перечень нормализаций и проверок

1. Обязательные поля товара проверяются по типам. Для id/title/image/category требуется непустая строка; description может быть пустой строкой, но не null/undefined. Пропущенные поля не заполняются выдуманными значениями.
2. price допускает null или конечное неотрицательное число, включая 0. Строковые числа не приводятся автоматически. NaN/Infinity/отрицательная цена отклоняются.
3. total должен быть безопасным неотрицательным целым и равняться длине items. Равенство — явная политика получения полного каталога; пагинация на этом этапе не реализована. Частичный/несогласованный список отклоняется.
4. Повторяющиеся id отклоняются до модели. Создаются новые объекты/массивы; дополнительные JSON-поля отбрасываются. API-данные не делят изменяемые ссылки с состоянием модели.
5. Изображение проверяется функцией разрешения URL, но IProduct.image сохраняет исходный путь согласно принятой архитектуре. Нет лишних HEAD/GET на каждый товар во время обычной нормализации.
6. Для POST строится отдельный DTO. `card` преобразуется в документированный `online`. payment=`cash` блокируется до HTTP кодом contract-unavailable, поскольку допустимое серверное значение не подтверждено.
7. POST содержит только payment/address/email/phone/total/items, строки trim, items копируется. Невалидные обязательные поля/сумма/список id не отправляются. Правильность суммы по ценам уже обеспечивает существующий OrderModel.
8. Подтверждение заказа проверяется как объект с непустым строковым id и конечной неотрицательной total, равной отправленной сумме. Из DTO возвращается существующий IOrderResult `{ total }`, без изменения интерфейса. Заказ и корзина не очищаются адаптером.

## 5. CDN

`resolveProductImage(image, cdnUrl)` принимает явный абсолютный HTTP(S)-адрес CDN и не обращается к DOM. Реальный путь `/5_Dots.svg` разрешается в `https://larek-api.nomoreparties.co/content/weblarek/5_Dots.svg`.

Абсолютные HTTP(S) URL остаются неизменёнными, включая query/fragment. Короткий путь с ведущим `/` трактуется относительно папки CDN, а не корня origin. Уже префиксированный путь `/content/weblarek/file.svg` не дублирует CDN. Повторные слеши при соединении относительного пути убираются. Не допускаются data/javascript, URL с credentials, protocol-relative URL, управляющие символы/обратные слеши, `..`, закодированные разделители и неверная percent-кодировка. Протокол `https://` не повреждается.

## 6. Обработка ошибок

ShopApiError содержит code и понятное сообщение, без включения сырой ошибки сервера или внутренних сетевых подробностей. Коды: invalid-data, request-failed, configuration, contract-unavailable.

Исходный Api не возвращает HTTP status вместе с ошибкой и пытается разобрать ошибочный HTTP-ответ как JSON. Поэтому 502 с HTML превращается в SyntaxError и обозначается invalid-data так же, как повреждённый JSON при HTTP 200. Числовой HTTP-код адаптер не выдумывает. Api оставлен без изменений по ограничению этапа.

При ошибке запроса/проверки данных модель не очищается. Автоматических повторов GET/POST нет. Поддержка AbortSignal/idempotency и гарантии exactly-once не заявляются; если сервер создал заказ, но ответ потерян, повтор может создать дубль.

## 9. Что не подтверждено и что проверяет HEAD

- Полный enum payment, особенно значение для оплаты при получении. Пока `cash` гарантированно не отправляется. Нужна документация поставщика/курса с явным значением либо согласованная отдельная проверка этого режима.
- Новая реальная покупка и её успешный POST end-to-end не выполнялись. Схема online-запроса и подтверждения взята у самого сервера и проверена контролируемыми ответами.
- Полная формальная JSON Schema, пагинация/полнота будущих каталогов, исчерпывающий список ошибок, дополнительные ограничения полей, idempotency и таймауты не подтверждены.
- Не проверена новая Windows-сборка/запуск новых файлов. До UI нет оснований объявлять магазин работающим в браузере.

HEAD проверяет сохранение исходных контрактов, разделение unknown/DTO/модели, политику отказа на повреждённые данные, ограничение cash, результаты live-проверки и корректность общего ZIP. Этап 4 самостоятельно не начинается.
