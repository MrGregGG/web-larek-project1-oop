## 4. Открытые вопросы и дефекты

### A. Незавершённая ветка cash — функциональный вопрос перед сдачей

В HTML и PaymentMethod доступны card/cash, OrderModel считает оба выбора допустимыми. Но src/services/orderData.ts:9–13 безусловно отклоняет cash до HTTP. Это корректная защита от выдуманного протокола, **но не реализованная успешная покупка выбранным способом**. Исходное ТЗ требует выбора оплаты и рабочего оформления; точных wire-значений оно не сообщает. Утверждать, что сам реальный сервер не поддерживает наличные, оснований нет: ограничение находится в текущем адаптере и подтверждённых проектом источниках.

Необходимое решение: найти официальный контракт или подтверждение курса для второго способа. Если он подтверждён — точечно добавить правильное преобразование и контролируемые положительные/отрицательные тесты. Если подтверждения нет — получить решение HEAD/проверяющего о допустимости ограничения и явно объяснить его пользователю до финальной отправки. Скрытие кнопки или имитация успеха сами по себе не делают требование выполненным. Случайные wire-значения и реальные тестовые POST запрещены.

### B. Проверка production Windows ещё не закрыта

37 сценариев запускают координатор с контролируемым транспортом через тестовый entry. Они не заменяют 8 сценариев загрузки настоящего dist/main.js через HTTP. Дополнительно нужно открыть обычный APP_URL, проверить реальный каталог/изображения/CORS/консоль и пройти доступные действия до отправки. Успех и ошибки отправки проверять только на CONTROLLED_CHECK_URL. Размер main.js в Windows не обязан равняться Linux-значению; файл должен быть непустым, содержать приложение и реально исполняться.

### C. Документация для сдачи

README.md:1–42 остаётся стартовым: нет фактической архитектуры/ссылки на её документ, методов классов и событий, инструкции API_ORIGIN, тестов, различия обычного/контролируемого запуска и ограничений оплаты. Подробная архитектура уже существует в другом документе — она не отсутствует, но точка входа для проверяющего не подготовлена.

В исторических разделах и комментариях src/types/index.ts остались сведения этапа 1 о неподтверждённом API/id. Фактически DTO и проверка id появились на этапе 3. Финальная документация должна явно разделять историю и текущее состояние. Не менять состав интерфейсов ради правки текста.

### D. Прежний технический долг

Полный npm run lint сохраняет 2 ошибки Function и 4 предупреждения в events.ts/utils.ts. При дополнительном --strict остаётся utils.ts:49 с потенциальным null у firstElementChild. Это существовавшие проблемы, не дефекты нового координатора. Для чистой сдачной проверки разумны минимальные исправления типов/защиты null с сохранением поведения и полного набора регрессий. Глобальное включение strict, переписывание EventEmitter, отключение правил и массовый автофикс не входят в план.

npm ci на Windows теперь подтверждён; прежний отказ Linux/npm 11 нельзя автоматически объявлять общей неисправностью проекта и «лечить» обновлением рабочего lock-файла. Сначала записать версии Node/npm и воспроизводимый целевой запуск. Предупреждения Sass/размера шрифтов не равны ошибке сборки и не требуют обновления зависимостей ради косметики.

### E. Воспроизведённый условный дефект destroy

В src/app.ts:361–378 destroy перебирает View; Modal стоит перед Page. Если внешний подписчик переданной шины бросает исключение в modal:closed, Modal.destroy снимает свои обработчики через finally, но цикл createApp прерывается и до Page.destroy не доходит.

Read-only аудит выполнил временную DOM-пробу без правки проекта: создать приложение с внешней шиной, открыть корзину, подписать бросающий исключение callback на modal:closed, вызвать app.destroy. Результат: исключение передано наружу; Page остаётся locked; retry-узел остаётся; клик по иконке корзины после destroy всё ещё публикует basket:open (1 событие). Обычный путь с собственными подписчиками при этом ранее прошёл 37/37.

Это условный дефект надёжности, не отсутствие основного магазина. Рекомендуемое точечное исправление этапа 7: гарантировать cleanup всех собственных View даже при исключении одного destroy, сохранив допустимую передачу ошибки вызывающему коду; добавить один воспроизводящий тест. В этой задаче исправление **не выполнялось**.
